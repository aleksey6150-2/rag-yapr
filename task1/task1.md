# Задание 1. Исследование моделей и инфраструктуры

## 1. Сравнение LLM-моделей

### Локальные модели (Hugging Face)

Для RAG в 2026 году разумные кандидаты: **Llama 3.3 70B Instruct**, **Qwen2.5 32B / 72B**, **Mistral Small/Large**, **Gemma 2 27B**. Для лёгких сценариев — **Llama 3.1 8B**, **Phi-3.5**.

| Параметр | Оценка |
|---|---|
| Качество | 70B-класс модели на RAG-задачах сопоставимы с GPT-4o при хорошем промптинге; 7–13B заметно слабее, но для FAQ-сценариев хватает. |
| Скорость | Зависит от железа. На A100/H100 + vLLM — 30–100 tok/s, латентность 1–3 с на ответ. На L4/RTX 4090 — 7B-модели работают комфортно, 70B уже тяжело. |
| Стоимость | Высокий CapEx (GPU-сервер), низкий OpEx. На горизонте года — обычно дешевле облака при стабильной нагрузке. Сложно прогнозировать стоимость инцидентов и обслуживания. |
| Развёртывание | Сложно: нужны MLOps-компетенции, vLLM/TGI/Ollama, мониторинг GPU, квантизация. Команда DevOps без ML-опыта потратит 2–4 недели на стабилизацию. |
| Конфиденциальность | **Главный плюс** — данные не покидают периметр. Для NDA-документов это единственный приемлемый вариант. |

### Облачные модели

Актуальные на апрель 2026 цены:

| Модель | Input ($/1M токенов) | Output ($/1M токенов) | Примечание |
|---|---|---|---|
| GPT-4o | 2.50 | 10.00 | стабильный legacy-флагман |
| GPT-4o-mini | 0.15 | 0.60 | хорош для FAQ-сценариев |
| GPT-5.4 (флагман) | от 1.75 | от ~10 | новый флагман, EU residency +10% |
| GPT-5.4 Mini | 0.75 | ~3 | оптимальный mid-tier |
| YandexGPT Pro 5.1 | ~$0.011/1K (~$11/1M) | то же | 0.80 ₽/1K токенов |
| YandexGPT Lite | ~$0.003/1K (~$3/1M) | то же | 0.20 ₽/1K токенов |

| Параметр | OpenAI | YandexGPT |
|---|---|---|
| Качество | GPT-5.4 / 4o уверенно покрывают многоязычные RAG-сценарии, в т.ч. финский/эстонский | Сильнее в русском, на финском/эстонском заметно слабее |
| Скорость | 0.5–2 с на ответ через API, EU endpoint | Сравнима, но регион — РФ/Казахстан |
| Стоимость | Прозрачная per-token, есть Batch API (-50%) и кэш-промпт (-50%) | Дешевле OpenAI в целом, но малорелевантно из-за блокеров |
| Развёртывание | Очень простое: ключ + SDK | Простое, но нужен Yandex Cloud аккаунт |
| Конфиденциальность | Есть EU residency, DPA, opt-out из обучения | Не подходит для EU-юрисдикции |

### Расчёт стоимости облачного LLM на кейсе QuantumForge

Допущения: 200 сотрудников × 5 запросов/день × 22 рабочих дня = **22 000 запросов/мес**. Средний запрос: 4000 input токенов (контекст из RAG) + 400 output токенов.

- **GPT-4o-mini**: 22000 × (4000 × $0.15 + 400 × $0.60) / 1 000 000 ≈ **$18/мес**
- **GPT-4o**: 22000 × (4000 × $2.50 + 400 × $10) / 1 000 000 ≈ **$308/мес**
- **GPT-5.4 Mini (EU residency, +10%)**: ≈ **$95/мес**

Это микроскопические суммы по сравнению с экономией на FTE. Если 200 инженеров экономят даже 1 час/неделю каждый при средней ставке €60/ч — это **~€48 000/мес** возвращённых рабочих часов. Кейс окупается на любой облачной модели.

**Промежуточный вывод по LLM:** вопрос «сколько стоит LLM» в этом кейсе вторичен. Первичен вопрос **«что можно отправлять во внешний API, а что нельзя»**. Отсюда естественно вытекает гибридная архитектура с маршрутизацией.

## 2. Сравнение моделей эмбеддингов

### Локальные (Sentence-Transformers / BGE / E5)

Релевантные мультиязычные модели:
- **BGE-M3** (BAAI) — 1024 dim, поддерживает 100+ языков, отлично работает с длинными чанками
- **multilingual-e5-large** — 1024 dim, проверенная мультиязычная модель
- **nomic-embed-text-v1.5** — 768 dim, открытая лицензия
- **jina-embeddings-v3** — 1024 dim, хороша для технических текстов

| Параметр | Оценка |
|---|---|
| Скорость индексации | На CPU (8 потоков) — ~50–200 чанков/с. На GPU (даже T4) — 1000+ чанков/с. Полная переиндексация 21k документов = 1–2 ч на CPU, 10–20 мин на GPU. |
| Качество поиска | BGE-M3 и multilingual-e5-large на MTEB **обходят** OpenAI text-embedding-3-large на мультиязычных задачах. На английском — паритет или чуть хуже. |
| Стоимость | Бесплатно. Нужны ~16 ГБ RAM + опционально GPU для скорости. |
| Конфиденциальность | Полная — данные не уходят. |

### Облачные (OpenAI Embeddings)

- **text-embedding-3-small**: $0.02 / 1M токенов, 1536 dim (можно сжать)
- **text-embedding-3-large**: $0.13 / 1M токенов, 3072 dim

| Параметр | Оценка |
|---|---|
| Скорость индексации | Ограничена rate limits API. С батчингом — 500–2000 чанков/с. Для 21k документов — пара часов. |
| Качество поиска | Очень хорошее на английском, на финском/эстонском уступает BGE-M3. |
| Стоимость | 21 000 документов × ~3 чанка × ~500 токенов = ~31M токенов → разовая индексация = **$0.62 (small)** или **$4 (large)**. Обновления +400 стр./мес ≈ копейки. |
| Конфиденциальность | Каждое слово документации уйдёт в OpenAI. **Для NDA-материалов недопустимо.** |

### Расчёт по объёму

| Метрика | Локальный BGE-M3 | OpenAI text-embedding-3-small |
|---|---|---|
| Разовая индексация 21k док | ~1.5 ч (CPU) / 15 мин (GPU) | ~30 мин (по rate limit) / $0.62 |
| Месячный прирост (400 стр.) | ~1 мин | ~$0.01 |
| Стоимость 1 года | $0 + амортизация железа | ~$1 + хостинг |
| Векторная размерность | 1024 | 1536 (сжимаемо до 256) |
| Multilingual quality | Высокое | Среднее |

**Вывод по эмбеддингам:** для QuantumForge **локальные эмбеддинги — почти безусловный выбор**. Они бесплатны, лучше работают с финским/эстонским/шведским и решают проблему конфиденциальности на уровне индексации. Эмбеддинги — это самый «горячий» путь данных: облако пришлось бы пропустить через себя весь корпус, что для NDA-материалов недопустимо.

## 3. Сравнение векторных баз: ChromaDB vs FAISS

### FAISS (Facebook AI Similarity Search)

FAISS — это **библиотека**, а не СУБД. Реализует HNSW, IVF, PQ-индексы. Запускается внутри процесса.

| Параметр | Оценка |
|---|---|
| Скорость поиска | Эталонная — десятки тысяч запросов/с на CPU при HNSW. На больших корпусах быстрее многих БД. |
| Скорость индексации | Очень высокая, особенно на GPU-сборке (faiss-gpu). |
| Сложность внедрения | Низкая для прототипа: `pip install faiss-cpu`, индекс в памяти. **Высокая для продакшена**: нет встроенной персистентности (нужно save/load в файл), нет фильтрации по метаданным «из коробки», нет одновременного чтения/записи. Метаданные приходится хранить параллельно (dict / sqlite) и склеивать вручную. |
| Удобство в работе | Низкоуровневое API. Нет инкрементальной перестройки HNSW (delete = пометка, под капотом не реальное удаление). |
| Стоимость | Сама библиотека бесплатна. Не требует отдельного сервиса — экономия на инфраструктуре. |
| Подходит для | Прототип, фиксированный корпус, embedded-режим, бенчмарки. |

### ChromaDB

Полноценная векторная БД с открытым исходным кодом. Под капотом — HNSW (через hnswlib) + SQLite/DuckDB для метаданных. Может работать в embedded-режиме (как FAISS) или как отдельный сервер.

| Параметр | Оценка |
|---|---|
| Скорость поиска | Чуть медленнее чистого FAISS на больших корпусах (накладные расходы на фильтрацию метаданных), но на масштабе 100k–1M чанков разница пренебрежимо мала. |
| Скорость индексации | Сопоставима с FAISS, чуть медленнее за счёт записи в SQLite. |
| Сложность внедрения | Низкая и для прототипа, и для продакшена. Из коробки: персистентность, метаданные, фильтрация (`where={"source": "confluence"}`), коллекции, multi-tenant. |
| Удобство в работе | Высокое: pythonic API, простой docker-образ, интеграция с LangChain в одну строку. Нормальные delete/update. |
| Стоимость | Open-source. Можно гонять в одном контейнере с ботом или в отдельном — на скейле QuantumForge достаточно одного экземпляра на 4–8 ГБ RAM. |
| Подходит для | Продакшен с многосорцовой документацией, метафильтрами, контролем доступа. |

### Сравнительная таблица

| Критерий | FAISS | ChromaDB |
|---|---|---|
| Скорость поиска (100k чанков) | ~5 мс p50 | ~10–20 мс p50 |
| Метаданные и фильтрация | Вручную | Из коробки |
| Персистентность | Save/load файла | SQLite/DuckDB, автоматически |
| Инкрементальные апдейты | Болезненно | Просто |
| Multi-tenancy / коллекции | Нет | Есть |
| Кривая обучения | Средняя (низкоуровнево) | Низкая |
| Production-ready без обвязки | Нет | Да |
| Стоимость | $0 | $0 |

### Что важно для кейса QuantumForge

База знаний многосорцовая: Confluence, GitHub, PDF, Zendesk, Google Drive. Бот должен **отвечать с указанием источника** (это и про SOC 2, и про доверие пользователей), фильтровать по типу/команде/языку, удалять устаревшие версии после релизов. Всё это требует метаданных и нормальных update/delete — сильная сторона Chroma.

С другой стороны, **ТЗ Практикума явно рекомендует FAISS** для прототипа и MVP в Docker — и это разумно: меньше зависимостей, проще запустить.

**Гибридная стратегия (рекомендую):**
- **MVP / прототип на спринт** — FAISS in-memory, обёрнутый в LangChain. Быстро поднять, показать работу.
- **Pilot и далее** — ChromaDB в отдельном контейнере с persistent volume. Миграция занимает несколько часов работы, т.к. абстракция LangChain `VectorStore` одинаковая.

## 4. Конфигурация сервера

Зависит от того, **где живёт LLM**. Рассмотрим три профиля.

### Профиль А — Cloud LLM + локальные эмбеддинги (рекомендуемый)

Нагрузка на сервер: только эмбеддинги, векторная БД, оркестрация.

| Ресурс | Спецификация | Обоснование |
|---|---|---|
| CPU | 8 vCPU (например, AWS `c7i.2xlarge` или Hetzner CCX33) | BGE-M3 на CPU отдаёт ~50–100 эмбеддингов/с в 8 потоков; для онлайн-запросов хватает с запасом |
| RAM | 32 ГБ | модель эмбеддингов ~2 ГБ + Chroma in-memory кэш + LangChain + Telegram-бот |
| GPU | Не требуется | BGE-M3 на CPU отвечает за ≤100 мс — в RAG это не bottleneck |
| Диск | 100 ГБ SSD | индекс на 100k чанков ≈ 2–4 ГБ, плюс логи и SQLite |
| Стоимость | ~€80–150/мес | сравните с €48 000/мес возвращённого рабочего времени |

### Профиль Б — Полностью локальный, малая модель (Llama 3.1 8B / Qwen 2.5 7B)

| Ресурс | Спецификация |
|---|---|
| CPU | 16 vCPU |
| RAM | 64 ГБ |
| GPU | 1× NVIDIA L4 (24 ГБ VRAM) или RTX 4090 |
| Диск | 200 ГБ SSD |
| Стоимость | ~€600–1200/мес в облаке, либо ~€4–6k разово при on-prem |

### Профиль В — Полностью локальный, большая модель (Llama 3.3 70B, квантизация AWQ/GPTQ Q4)

| Ресурс | Спецификация |
|---|---|
| CPU | 32 vCPU |
| RAM | 128 ГБ |
| GPU | 1× H100 80 ГБ или 2× A100 40 ГБ |
| Диск | 500 ГБ NVMe |
| Стоимость | ~€3000–6000/мес в облаке, либо ~€30–40k разово при on-prem |

## 5. Четыре варианта итоговой конфигурации

| # | Вариант | LLM | Эмбеддинги | Векторная БД | Сервер | TCO/год | Конфиденциальность | Time-to-MVP |
|---|---|---|---|---|---|---|---|---|
| 1 | **Cloud-first** | OpenAI GPT-5.4 Mini (EU) | OpenAI text-embedding-3-small | Chroma | Профиль А | ~€2.5k | ❌ всё уходит в OpenAI | 1 неделя |
| 2 | **Гибрид (рекомендуемый)** | OpenAI GPT-5.4 Mini (EU residency) + GPT-4o для сложных запросов | BGE-M3 локально | Chroma (FAISS на MVP) | Профиль А | ~€2.5–4k | ⚠️ только запросы пользователей и top-k чанки уходят к LLM, корпус — локально | 2 недели |
| 3 | **Полный on-prem (small)** | Llama 3.1 8B / Qwen 2.5 7B локально | BGE-M3 локально | Chroma | Профиль Б | ~€10–15k OpEx или €5k CapEx | ✅ полная | 4–6 недель |
| 4 | **Tiered (NDA-маршрутизация)** | Локальная Llama 8B для документов под NDA + GPT-5.4 Mini (EU) для публичных | BGE-M3 локально | Chroma с метатегом `confidentiality_level` | Профиль Б | ~€12–18k | ✅ оптимальная | 6–8 недель |

### Что выбираем и почему

**Финальная рекомендация — Вариант 2 (Гибрид) с дорожной картой к Варианту 4.**

Аргументация:

1. **Качество.** GPT-5.4-класс модели заметно сильнее любой open-source 7–13B на сложных RAG-запросах с многоязычными источниками. Это критично для разработчиков и аналитиков. Локальные 70B+ дотягивают, но требуют GPU-инфраструктуры.

2. **Стоимость.** Облачный LLM на этом объёме — ~€100–300/мес. CapEx на GPU-сервер для 70B — ~€30k. Окупаемость on-prem-сценария на этом объёме — годы. Локальные эмбеддинги при этом убирают самый дорогой по объёму путь данных (индексация всего корпуса).

3. **Конфиденциальность — ключевой trade-off.** В гибриде во внешний API уходит только **запрос пользователя + top-k релевантных чанков** (обычно 3–5 фрагментов по 500–1000 токенов), а не весь корпус. Это уже на порядок безопаснее cloud-first. С Azure OpenAI / OpenAI EU residency + DPA + opt-out из обучения — приемлемо для большинства внутренних доков.

4. **Дорожная карта к Варианту 4.** Документы с метатегом `nda=true` (определяется по источнику: например, всё из спейса Confluence «Customer Projects») при росте бота маршрутизируем на локальную Llama 8B. Это чистое расширение архитектуры, а не переделка.

5. **Time-to-value.** MVP можно показать через 1–2 недели и собирать обратную связь от пользователей, параллельно дозревая до production-конфигурации.

6. **SOC 2.** Chroma даёт метаданные источника → каждый ответ имеет ссылки → аудитор видит полную трассу. С FAISS это пришлось бы строить руками.

## 6. Выбор векторной БД (главный ответ задания)

**На MVP / спринт-сдачу: FAISS** (как и предлагает методичка).
**На пилот и продакшн: ChromaDB.**

### Почему FAISS на MVP

- Минимум зависимостей: одна библиотека, in-memory, не нужен отдельный контейнер.
- Соответствует ТЗ Практикума и базовому `docker compose.yml` (бот + FAISS).
- Скорость поиска — эталонная.
- Достаточно для сдачи задания и демонстрации работы.

### Почему ChromaDB на продакшн для QuantumForge

1. **Метаданные и фильтрация.** Бот должен фильтровать по `source` (Confluence/GitHub/Zendesk), `team` (R&D/Support/Sales), `language` (en/fi/et), `version` (актуальная/устаревшая). В FAISS это пришлось бы строить параллельно через SQLite и склеивать вручную — потенциальный источник багов и расхождений.
2. **Жизненный цикл контента — основная боль из ТЗ.** Документация устаревает через 2–3 месяца после релиза. Нужны нормальные `update`/`delete` по идентификатору документа. В FAISS HNSW настоящего удаления нет, со временем индекс «гниёт» и требует пересборки.
3. **SOC 2 / аудит.** Каждый ответ должен ссылаться на источник. Chroma хранит метаданные рядом с вектором — одна точка истины. FAISS требует синхронизировать два хранилища, что удлиняет процедуру SOC 2 review.
4. **Multi-tenancy и масштабирование на другие команды.** Цель «масштабировать решение на другие команды/проекты/клиентов» из ТЗ компании — это коллекции в Chroma. В FAISS пришлось бы городить менеджер индексов руками.
5. **Операционная зрелость.** Chroma имеет официальный docker-образ, persistent volume, REST/Python клиент, простой бэкап (директория с SQLite). Команда DevOps без ML-опыта поддержит без проблем.
6. **Производительность.** На горизонте до ~1М чанков (то есть в десять раз больше текущего корпуса) разница с FAISS — единицы миллисекунд, что несущественно для UX чата с LLM, где сама генерация занимает 1–3 секунды.

### План миграции FAISS → Chroma

Обе БД покрыты абстракцией LangChain `VectorStore`. Замена выглядит так:

```python
# было
from langchain_community.vectorstores import FAISS
vectorstore = FAISS.from_documents(docs, embeddings)

# стало
from langchain_chroma import Chroma
vectorstore = Chroma.from_documents(
    docs, embeddings,
    persist_directory="./chroma",
    collection_metadata={"hnsw:space": "cosine"}
)
```

Перенос индекса = повторный embedding корпуса (~15 мин на GPU, ~1.5 ч на CPU). Никаких ломающих изменений в логике ретривера и промптах.

Для RAG-бота QuantumForge выбираем **гибридную архитектуру**: BGE-M3 для локальных эмбеддингов + Chroma как векторная БД (FAISS на MVP-спринт) + OpenAI GPT-5.4 Mini с EU residency как LLM. Для документов под NDA — задел на локальную Llama 8B и маршрутизацию по метатегу `confidentiality_level`. Сервер — 8 vCPU / 32 ГБ RAM / 100 ГБ SSD без GPU. Бюджет инфраструктуры — ~€2.5–4k/год против ~€500k/год возвращённого рабочего времени 200 инженеров.
